# 주차장 여석 판별 2D 맵 (컴퓨터비전 3조)

삼각대로 고정해 찍은 교내 주차장 영상에서 차를 검출합니다. 차가 바닥에 닿는 점(**지면 접점**)을 Homography로
**위에서 본 2D 지도**에 옮긴 뒤, 칸마다 비었는지 판정합니다. 결과는 원본 영상과 지도를 나란히 보여주는 영상과
칸 상태 CSV로 나옵니다.

- **제안 방식**: 바닥(주차선)은 Homography로 펴고, 높이가 있는 차는 바닥에 닿는 부분(지면 접점, 차 바닥 영역)만 지도로 옮겨 지도 위에서 판정합니다.
- **비교 기준**: 논문 ② 방식. 영상 위 칸 폴리곤 안에 박스 중심점이 들어가면 점유로 봅니다.
- 설계 기준과 결정 이유는 [CLAUDE.md](CLAUDE.md)에 있습니다.
- **새 영상을 추가하는 팀원은 [docs/TEAM_GUIDE.md](docs/TEAM_GUIDE.md)를 따라 하세요** (촬영 → 등록 → 점 찍기 → 확인 → 라벨링 → 평가).

1차·2차·3차는 쌓아 가는 설계 단계입니다. **기본 설정(최종 시스템)은 세 단계가 모두 적용된 상태**입니다.

| 단계 | 더해지는 것 | 상태 |
|---|---|---|
| 1차 | 지면 접점 → 2D 지도에서 칸 점유 판별 (빈칸 초록 / 점유 빨강 / 판단불가 회색) | 완료, 평가 완료 |
| 2차 | 차 바닥 영역 + 칸별 겹침 비율: 20% 이상 걸친 옆 칸도 점유, 25% 이상 두 칸에 걸치면 침범(노랑) | 적용, 침범 표시는 성능 한계 있음 |
| 3차 | ByteTrack 추적 + 통로 정지 시간 → 불법주차(주황) | 적용, 평가용 영상 필요 |

## 1. 설치

Ubuntu, Python 3.10 이상, NVIDIA GPU 권장 (RTX 4060에서 확인).

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
pip install -e .
pytest -q          # 합성 데이터 단위 테스트 59개
```

- 검출 모델(`yolo26x-seg.pt`, COCO 사전학습)은 처음 실행할 때 `models/`에 자동으로 받아집니다. 학습 데이터는 필요 없습니다.
- 데이터(`data/`), 영상, 모델 가중치, 결과(`outputs/`)는 저장소에 넣지 않습니다. 영상은 공유 드라이브에서 받습니다.
- 설정값(모델, 해상도, 임계값, 칸·차 크기)은 모두 [configs/default.yaml](configs/default.yaml)에 있습니다.

## 2. 용어와 폴더 구조

| 용어 | 뜻 |
|---|---|
| lot | 주차장. 주차장마다 지도(`map.json`)가 1개입니다. |
| cam | 삼각대 한 위치. 위치마다 Homography `H`가 1개입니다. |
| clip | 영상 파일 1개. 같은 cam의 clip은 같은 H를 씁니다. |

```
data/
  lots/<lot>/map.json, map_bev.png             # 칸·통로 좌표 (m), 탑뷰 배경
  cams/<lot>_<cam>/H.json, ref_frame.png        # 대응점, H, 재투영 오차
  clips/<clip_id>/video.mp4, meta.json          # meta: lot, cam, condition, valid_sec, split
  clips/<clip_id>/gt_frames/, gt_occupancy.csv  # 라벨링용 프레임, 정답
outputs/<clip_id>/
  detections.jsonl                              # 검출 캐시 (한 번만 돌림)
  occupancy.csv, split_view.mp4, events.csv     # 칸 상태, 결과 영상, 불법주차 이벤트
```

`meta.json` 예:
```json
{"lot": "lotA", "cam": "lotA_cam3", "condition": "mid", "valid_sec": [24.0, 853.0], "split": "tune"}
```
`valid_sec`는 카메라가 고정된 구간입니다(촬영 시작·끝의 흔들림 제외). `split`은 `tune`(임계값 조정용) 또는 `test`(최종 보고용)입니다.

## 3. 실행 방법

GUI 도구(setup_cam, build_map, label_gt)는 OpenCV 창으로 열리고, 화면에 키 조작법이 나옵니다.
공통 키는 `u` 되돌리기, `s` 저장, `q` 종료입니다.

### 3.1 새 카메라 위치 설정 (cam마다 1회)
```bash
python tools/setup_cam.py --clip data/clips/lotA_cam3_mid
```
1. 선이 잘 보이는 주차칸 모서리를 클릭하고, 터미널에 그 점의 지도 좌표(m) `x y`를 입력합니다. **6개 이상**, 화면 양 끝과 여러 줄에 넓게 찍습니다.
   - 점이 4개 이상 모이면 화면 위쪽에 커서 위치의 지도 좌표가 나옵니다. 다음 점의 좌표를 찾을 때 참고하면 됩니다.
   - 같은 주차장의 두 번째 cam부터는 **첫 cam과 같은 좌표 기준**으로 입력해야 합니다.
2. `v`로 검증점 2~4개를 찍습니다. H 계산에 쓰지 않고 오차 확인에만 씁니다.
3. `s`로 저장합니다. 그 주차장의 첫 cam이면 지도 뼈대와 탑뷰 배경도 함께 만들어집니다.

**같은 주차장의 새 촬영 위치는 자동으로** (`--auto`, 2026-11-26):
```bash
python tools/setup_cam.py --clip data/clips/lotA_cam4_mid --auto            # 자동 대응점 -> 화면에서 확인 후 s
python tools/setup_cam.py --clip data/clips/lotA_cam4_mid --auto --no-gui   # 확인 없이 바로 저장
```
- 이미 설정한 cam들의 기준 프레임과 바닥 특징점(SIFT)을 맞춰 대략 H를 구합니다. 일치점이 가장 많은 cam을 기준으로 씁니다.
- 그 cam들이 찍어 둔 주차선 모서리를 새 영상에서 주변 패치 매칭으로 정밀하게 다시 찾아 대응점으로 넣습니다.
- 화면에서 격자와 점을 확인하고, 틀린 점은 `u`로 지우거나 직접 추가한 뒤 `s`로 저장합니다.
- 시점이 너무 달라 일치점이 50개 미만이면 실패로 알리고, 그때는 손으로 찍습니다.
- 검증점도 자동으로 찾은 점이라 표시되는 오차가 실제보다 작습니다. `map_overlay.png`를 꼭 눈으로 확인하세요.
- 시험 결과 (lotA 세 cam을 하나씩 H를 모른다고 보고 나머지 두 cam으로 자동 계산):

| cam | 자동 H 오차 (손 대응점 기준, 평균 / 최대) | 손 H | 점유 결과 (자동 H) | 점유 결과 (손 H) |
|---|---|---|---|---|
| cam1 (test) | 0.09 / 0.29m | 0.03 / 0.08m | 정확도 1.000 | 1.000 |
| cam2 (test) | 0.16 / 0.89m | 0.05 / 0.16m | 정확도 1.000 | 1.000 |
| cam3 (tune) | 0.09 / 0.29m | 0.04 / 0.10m | 치명 48 / 오판 26, 침범 장면 26·39·0 | 49 / 5, 25·40·0 |

  자동 H는 손 H보다 2~3배 부정확하지만, 테스트 영상의 점유 결과는 같았습니다. cam3은 빈칸→점유 오판이 늘었습니다.

### 3.2 지도에 칸 그리기 (주차장마다 1회)
```bash
python tools/build_map.py --lot lotA --cam lotA_cam3
```
- `1` 줄 모드: 첫 칸 앞 모서리 → 줄 끝 → 첫 칸 뒤 모서리를 클릭한 뒤, 칸 수와 이름(예: `10 A`)을 입력합니다.
- `2` 다각형 모드: 불규칙한 칸, 통로, 금지구역을 직접 클릭합니다.
- 칸은 **주차선 중심선** 기준으로 그립니다. 이웃 칸 사이에 틈이 없어야 합니다.
- 두 번째 창에 원본 영상 위에 지도를 되돌려 그린 그림이 나옵니다. 실제 선과 맞는지 확인하세요.

### 3.3 영상 처리 (clip마다)
```bash
python -m parking.pipeline --clip data/clips/lotA_cam3_mid             # 칸 상태 CSV + 결과 영상
python -m parking.pipeline --clip data/clips/lotA_cam3_mid --no-video  # CSV만 (빠름)
```
- 처음 실행하면 YOLO 검출을 돌려 `detections.jsonl`에 저장합니다. 이후에는 이 캐시를 읽어 판정만 다시 합니다.
- 결과 영상 `split_view.mp4`의 왼쪽은 원본 영상에 칸 상태와 검출 결과를 겹친 것이고, 오른쪽은 탑뷰 지도에 칸 상태, 접점, 통로를 그린 것입니다.

### 3.4 정답 라벨링
```bash
python tools/sample_frames.py --clip data/clips/lotA_cam3_mid --every-sec 10
python tools/label_gt.py --clip data/clips/lotA_cam3_mid
```
- 칸 안쪽 바닥을 클릭할 때마다 상태가 바뀝니다: 0 빈칸 → 1 점유 → 2 침범(선에 걸친 차) → -1 판단불가 → 0
- **클릭한 변경은 뒤 프레임에도 이어서 적용됩니다.** 차가 떠난 프레임에서 다시 클릭해 되돌려야 합니다.
- 시스템 예측은 화면에 보이지 않습니다. 테스트용 clip은 결과 영상을 보기 전에 라벨링해야 공정합니다.
- 특정 구간만 촘촘히 뽑으려면: `--every-sec 2 --start 455 --end 705 --max 200`

### 3.5 평가

python eval/evaluate.py --clips data/clips/lotA_* --split test    # 지표 상세 (줄·조건별)

| 방식 | 빈칸 Precision | 점유 Recall | Accuracy | 빈자리 수 MAE | 점유→빈칸 (치명적) |

| 논문 ② (박스 중심) | 0.814 | 0.708 | 0.852 | 4.76 | 1,202 |

- "점유→빈칸"은 **차가 있는 칸을 빈칸으로 안내한 횟수**입니다. 사용자에게 가장 치명적인 실수입니다.
  - 논문 ② 대비: 테스트 305건 → 0건, 튜닝 1,202건 → 49건
- **1차 (지면 접점)의 효과**: 박스 중심은 차 높이만큼 카메라 반대쪽(뒤 칸)으로 밀려 찍히고, 지면 접점은 그렇지 않습니다.
  합성 실험(`tests/test_contact.py`, `tools/debug_synthetic.py`)에서 예측한 차이가 실제 영상에서도 확인됐습니다.
- **깊이 오프셋 0.9m**: 지면 접점은 차 바닥의 카메라 쪽 끝이라, 접점을 차 폭의 절반만큼 카메라 반대쪽으로 밀어 차 바닥 안쪽에 오게 합니다.
  1차만 기준 치명적 실수: 튜닝 131 → 91, 테스트 80 → 0.
- **2차 (차 바닥 영역)의 효과**: 1차는 차 한 대당 칸 하나만 표시해서, 선 밟은 차가 걸친 옆 칸은 빈칸으로 남았습니다.
  2차는 차 바닥 사각형이 20% 이상 겹친 칸을 모두 점유로 봅니다(튜닝 치명적 실수 91 → 49, 테스트는 둘 다 0).
  - 기준을 논문 ③의 15%로 하면 치명적 실수는 40건으로 더 줄지만, 사각형의 좌우 위치 오차 때문에
    바르게 선 차 옆의 빈칸을 점유로 보는 오판이 5건에서 27건으로 늘어납니다(튜닝). 그래서 20%로 정했습니다.
  - 통로를 가로지르는 차는 사각형을 가로로 눕힙니다. 접점이 통로에 있고 보이는 바닥 경계가 칸과 수직으로 3m 이상 길 때입니다.
    눕히지 않으면 세로 사각형이 앞 칸으로 뻗어 빈칸을 점유로 봅니다(튜닝 빈칸→점유 27 → 3).
- 남은 오류: 거의 모두 cam3 연출 구간(7분 37초~11분 38초)에서 움직이거나 비스듬히 선 차입니다.
- 처리 속도:
  - 검출: 약 0.33초/프레임 (RTX 4060, 영상 디코딩 포함)
  - 판정, 추적, 결과 영상 생성: 약 0.08초/프레임
  - 판정만 (cam3, 프레임당 차 약 19대, 2026-11-26): 1차만 10ms, 사각형 30ms, 융합(기본, 3D 박스 포함) 57ms
- 검출 fps (2026-11-26부터 기본 10fps): 2fps와 결과가 같습니다. cam3 치명 50 / 오판 5 (2fps 49 / 5), 테스트 정확도 1.000.
  결과 영상은 원본 30fps 모든 프레임에 직전 결과를 덧그려 실제 속도로 재생됩니다 (`render.full_fps`).
  - 논문 ③은 장당 약 1.5초

### 4.3 2차: 칸 침범 판별
- 방법: 마스크 아래 경계를 지도에 옮기고, 카메라 쪽 끝을 기준으로 표준 차 크기(1.8×4.7m) 사각형을 칸 방향에 맞춰 놓습니다.
  - 겹침 비율은 **차 면적 기준**으로 계산합니다. 칸이 차보다 커서 칸 면적 기준이면 꽉 찬 차도 70%밖에 안 됩니다.
  - 20%(`tau_occupy`) 이상 겹친 칸은 모두 점유(빨강)입니다. 가장 많이 겹친 칸 말고도 25%(`tau_straddle`) 이상 겹친 칸이 있으면 두 칸 모두 침범(노랑)입니다.
- 결과(침범 장면 단위: 정답 침범 칸과 예측 침범 칸이 하나라도 겹치면 맞음):

| clip | 침범 기준 | 맞음 | 놓침 | 오경보 장면 |
|---|---|---|---|---|
| cam3 연출 구간 (tune, 침범 장면 65장) | 0.15 (논문 ③) | 35 | 30 | 24 |
| cam3 연출 구간 (tune) | 0.20 | 28 | 37 | 4 |
| cam3 연출 구간 (tune) | **0.25 (채택)** | **27** | 38 | **2** |
| cam3 연출 구간 (tune) | 0.30 | 19 | 46 | 0 |
| cam1·cam2 (test, 침범 없음, 79장) | 0.25 | – | – | 11 |

- **한계**:
  - 차 바닥 사각형의 좌우 위치 오차(±0.3~0.5m)가 칸 안 여유(0.34m)와 비슷합니다. 그래서 살짝 걸친 차와 바르게 선 차를 구분하기 어렵습니다.
  - 연출한 차는 대부분 칸과 비스듬히 서 있는데, 사각형은 칸 방향으로 가정합니다. 보이는 경계로 차 방향을 추정해 보았지만 개선되지 않았습니다.
  - 테스트 오경보 11장(cam1 B06·B07)은 뒤 차(B07)가 앞차(B06 흰 SUV)에 가려져, 앞차 윗면과 만나는 경계가 바닥으로 투영되어
    사각형이 1m 옆으로 밀리기 때문입니다. 앞차 마스크에 닿는 점을 가려진 점으로 보고 반대쪽 끝에서 사각형을 펴 보았지만,
    튜닝 clip에서 개선이 없고 기준 거리(1~3px)에 따라 결과가 크게 흔들려 넣지 않았습니다.
- 침범 기준 0.25는 cam3에서 골랐습니다. 최종 성능을 보고하려면 다른 위치나 다른 날의 연출 영상이 필요합니다.

### 4.4 3차: 불법주차 탐지
- 방법:
  - 검출 캐시(2fps)에 ByteTrack을 붙여 차마다 지도 위 궤적을 만듭니다.
  - 통로 안에서 5초 평균 속도가 0.3m/s 미만인 상태가 60초 이상 이어지면 이벤트입니다.
  - 통로는 마주 보는 칸 줄 사이에 자동 생성합니다(AISLE1 = A~B줄, AISLE2 = C~D줄).
- 결과:
  - 현재 세 clip에는 통로 장기 정차가 없어 이벤트 0건, 오경보 0건입니다.
  - 기준을 10초로 낮추면 cam3 9분 42초~10분 17초 AISLE2의 35초 정차 1건이 잡힙니다. 추적과 정지 판정은 동작합니다.
- **평가 대기**: 통로 1분 이상 정차, 통과, 잠깐 멈춤 장면을 연출해 찍고 `gt_events.csv`를 만들어야 합니다.

### 4.5 관련 논문 방식과 비교 (2026-11-26)
같은 검출 캐시, 같은 GT로 설정만 바꿔 실행했습니다(`python eval/compare.py`). 기준값은 모두 cam3(튜닝용)에서 골랐습니다.

| 방식 | cam3 치명 / 오판 | cam3 침범 장면 (맞음/놓침/오경보) | test 정확도 | test 오판 / 침범 오경보 |
|---|---|---|---|---|
| **최종 (제안, 융합)**: 점유 = 사각형, 침범 = 사각형과 3D 박스 둘 다 침범일 때만 | **49 / 5** | **25 / 40 / 0** | **1.000** | **0 / 0** |
| 사각형만 (2026-11-26 이전 기본) | 49 / 5 | 27 / 38 / 2 | 1.000 | 0 / 11 |
| Laptiev 외 (2026): 열마다 가장 아래 픽셀 평균 + 칸 안 접점 비율 | 97 / 0 | 3 / 62 / 89 | 1.000 | 0 / 46 |
| 3D 박스 맞추기 (BoxCars 계열, H + 내부 파라미터로 카메라 복원) | 49 / 5 | 27 / 38 / 0 | 0.989 | 32 / 21 |
| Masmoudi 외: 칸 3D 상자의 안 가려진 부분 | 1,075 / 208 | – | 0.720 | 175 / – |
| 논문 ② (박스 중심) | 1,202 / 211 | – | 0.860 | 109 / – |

- **Laptiev 외**는 우리와 가장 가까운 논문입니다(마스크 아래 경계 + Homography).
  - 점유는 우리 1차와 비슷합니다(cam3 치명 97 vs 91).
  - "잘못 주차" 판정은 우리 영상에서 동작하지 않습니다. 비스듬한 시점에서는 가장 아래 픽셀들이 차 바닥의 카메라 쪽 끝선, 즉 칸 경계선 위에 몰려서 바르게 선 차도 칸 밖 비율이 높게 나옵니다.
- **3D 박스**는 차 방향까지 추정할 수 있습니다.
  - cam3에서는 제안 방식과 거의 같고, 테스트 clip에서는 나빴습니다.
  - 원인: 표준 크기 박스를 마스크에 맞추면 SUV처럼 크기가 다른 차나 먼 차에서 위치와 방향이 틀립니다.
  - 앞차에 가려진 cam1 B06·B07 침범 오경보는 사라졌습니다.
- **Masmoudi 외**처럼 영상 위 칸 영역으로 판정하면, 앞차가 뒤 칸 영역을 덮는 문제가 남아 논문 ② 수준에 그칩니다.
  지도 위에서 판정하는 제안 방식의 근거가 됩니다(Masmoudi 논문은 본문 서버에 접속하지 못해 요약만 확인했습니다).
- **융합 (2026-11-26)**: 사각형과 3D 박스는 틀리는 상황이 다릅니다(사각형은 기준점이 가려질 때, 3D 박스는 차 크기가 다를 때).
  그래서 침범은 둘 다 침범이라고 할 때만 침범으로 보고, 점유는 사각형 결과를 그대로 씁니다(`footprint.method: rect_and_box3d`).
  - cam3에서는 맞음 2장과 오경보 2장이 함께 줄어 거의 같습니다. 테스트에서는 침범 오경보가 11장에서 0장으로 줄었습니다.
  - **기본값으로 채택 (2026-11-26)**. cam3 기준으로는 비깁니다(진짜 침범 일부가 약 1초 늦게 노랑이 됨). 바르게 선 차를 침범으로 알리지 않는 쪽을 택했습니다.
    단, 이 아이디어는 테스트 영상의 B06·B07 오경보를 보고 떠올린 것이어서 테스트 수치(오경보 11 → 0)는 독립적인 검증이 아닙니다.
  - 화면: 흰 사각형 = 사각형 방식, 연분홍 = 3D 박스(원본에는 철사틀, 탑뷰에는 밑면).
  - Laptiev 외의 "여러 점 통계"로 사각형 기준점을 잡는 방법(열마다 가장 아래 픽셀의 5~20% 분위수)도 시험했습니다. cam3 오판이 5건에서 25~214건으로 늘어 채택하지 않았습니다.
- 논문 세 방식은 비교용 설정으로만 남겼습니다(`contact.mode: mask_lowest_mean` + `quality`, `footprint.method: box3d`, `slot_volume.enabled`).
- 탑뷰의 흰 박스(차 바닥 사각형)가 흔들리는 이유:
  - 서 있는 차 대부분은 흔들림이 1~5cm입니다.
  - 일부 차는 앞차에 가려지거나 마스크가 조각나서, 사각형 기준점(카메라 쪽 끝점)이 바뀌어 0.75~1.4m 튑니다.
  - 칸 색은 5프레임 다수결을 거치지만, 흰 박스는 프레임마다 계산한 값을 그대로 그립니다.

### 4.6 결과를 볼 때 주의할 점
- 데이터가 **주차장 1곳, 테스트 clip 2개**뿐입니다. 테스트 정확도 1.000은 "이 두 영상에서 모두 맞았다"는 뜻입니다.
- 깊이 오프셋 0.9m는 튜닝 clip에서도 나아서(1차만 기준 치명적 실수 131 → 91) 유지합니다. 처음 채택할 때는 테스트 결과를 보고 정했다는 점을 밝혀 둡니다.
- 점유·침범 기준(0.2, 0.25)은 튜닝 clip(cam3)으로만 골랐습니다. H나 지도가 바뀌면 겹침 비율이 달라지므로 다시 확인해야 합니다.
- 화면 밖이나 크게 가려진 칸은 판단불가로 빼고 정확도에서 제외했습니다. 테스트 clip의 커버리지는 약 81%(46칸 중 판정 가능한 칸 비율)입니다.
